# Implementation status

## M2a: local agent runtime — v0.2.0

Implemented on top of M1: three logical agents in a persistent Python worker; Coordinator-only delegation; six strict decision types; role-specific source read tools; saved observations, decisions, gateway verdicts and tool results; specialist intent/evidence reports; durable waiting/resumption; staff pause/retry controls; escalation and named staff acceptance; a staff timeline; forward database migration `0002`; an organiser JSON HTTP adapter; an explicitly labelled deterministic simulation; bounded retries, steps, request sizes and a shared live-call budget.

**Direct Claude addition (11 September):** `anthropic` mode uses the Messages API through the same typed decision/policy boundary. Migration `0003` preserves runs and allows the new provider. Both live providers and the one-call `model-check` share the persisted call limit and pacing. Provider credentials are backend-only. Follow [CLAUDE_SETUP.md](CLAUDE_SETUP.md). Direct Claude is now connected and tested with paid synthetic dental reviews. The direct adapter uses native JSON schema constraints, followed by the same strict parser and policy gateway. See [live validation](LIVE_CLAUDE_VALIDATION.md) for the outcomes, including earlier rejected attempts.

The organiser adapter follows the public starter-kit protocol and is tested using simulated HTTP responses. **The organiser endpoint has not been live-verified: its private team API URL/key have not been supplied.** Default mode is `mock`; model, mock and rule origins are distinct. No failed organiser call falls back to simulation.

Dental, myopia and antenatal cases use the shared runtime. A mixed date/preparation request exercises both specialists. Reply intent is unverified staff-entered demo data. A staff clinical flag creates a rule-origin RED handoff without requiring a model. Automatic clinical text/voice detection is pending.

**Unsupported RED correction (14 September):** model escalation choices now exclude `CLINICAL_REVIEW_REQUIRED`; the gateway independently denies it and preserves the rejected proposal. RED requires the existing explicit staff clinical flag. Routine confirmations with unavailable patient messaging/attendance updates use an AMBER administrative handoff. Handoff risk comes from the gateway, not the model's reason code. A scoped maintenance correction can appear as a separate journey event, preserving the original decision, verdict and original handoff classification.

M1 authentication, current clinic membership checks, Origin/CSRF protection, synthetic detection and leased foundation jobs remain. The old two-action draft validator is replaced by the current runtime contract; see [agent-decision-v1.json](contracts/agent-decision-v1.json).

## Completion and data boundary

**Patient conversation simulator (14 September):** new reviews display a persisted reminder, record an explicit synthetic attendance confirmation through a narrow mock clinic API, display an acknowledgement with exact approved notes, and complete without handoff after verifying receipt/message evidence. Coordinator delegates to Engagement and Preparation; the gateway owns authorization and completion checks. The source verifies appointment status/date/revision and prerequisite. No scheduling or booking change is made. Outgoing messages are local-only. Application migration `0004` adds `simulated_message`; source migration `sim0002` adds `sim_confirmation`. Idempotency, bounded source retries and late receipt recording cover interrupted writes. Fresh simulator tests preserve prior reviews. See [Patient simulator](PATIENT_SIMULATOR.md).

**Dynamic clinic simulator (13 September):** a separate local page combines schedule/status editing, synthetic notes and specialty-level available slots. The mock service persists three tables in its own `forget_lah_mock` database/user on the existing PostgreSQL server. Bootstrap provisions/migrates/seeds automatically; source migration `sim0001` is separate from application migration `0003`. The authenticated editor proxy uses clinic/Origin/CSRF checks and an internal key unavailable to the worker. Revision checks reject stale edits. Source URLs remain unchanged, with optional slot evidence added to context. Fresh `SIM-...` episodes are detected automatically; source edits do not restart existing cases or rewrite history. Reset supports the complete validated snapshot and recreates only eligible cases. See [Clinic simulator](CLINIC_SIMULATOR.md).

**Automatic startup and source loading (13 September):** new cases queue a review in the same transaction that completes the foundation job. A bounded recovery scan picks up older ready cases with no review. Existing reviews of any status are never restarted by this scan. The worker uses a reserved non-login principal with demo-clinic membership; bootstrap provisions it once without re-enabling revoked access. Gateway checks distinguish service authority from staff authority. Staff replies and handoff acceptance still require authenticated clinic access. `AGENT_AUTO_START_ENABLED` defaults to true; false stops new automatic registrations, not existing runs. Missing model configuration is shown as a paused review. No schema migration was required.

The first normal source read is a typed, persisted `origin=rule` tool action with zero model attempts, executed through the usual gateway/adapter and lease/version checks before model planning. Failed reads remain explicit results for recovery. Staff-flagged clinical escalation bypasses routine loading. Pending historical model steps retain their provenance. The initial-read optimisation applies to the first step of a new review; later context-dependent tool choices remain agent decisions. Both dashboard start buttons are removed; pause, retry, demo reply, handoff and optional reset controls remain. The authenticated manual-start API is retained for compatibility and engineering tests; the dashboard no longer calls it.

**Initial wait optimisation (12 September):** after Coordinator delegation to Engagement, the worker uses the current event's successful source context to save the fixed initial demo wait without a model call. This requires an active delegation and explicit disabled contact/write capabilities. The typed WAIT still passes the gateway and is persisted as `origin=rule`, with zero attempts and no live-call reservation. Missing/failed evidence retains the normal agent/recovery path; resumed replies still use model decisions. Existing historical decisions are preserved. The rule is one recorded step within the existing 24-step guardrail; that count is not a count of Claude calls.

**Demo reset addition (12 September):** `DEMO_RESET_ENABLED` defaults to false. When enabled, authorised demo-clinic staff can type `RESET` in the dashboard confirmation to atomically clear demo case/history records and recreate the three validated source candidates. Accounts, sessions, other clinics and usage accounting are preserved. Queued/running reviews must be paused first. The API checks Origin/CSRF, current membership, expected case IDs and fixture identity, and refuses reset if the source is unavailable. PostgreSQL table locks prevent overlapping resets/mutations; stale requests cannot reset a new generation. No migration is needed. See [DEMO_RESET.md](DEMO_RESET.md).

**Case Journey addition (12 September):** a separate read-only page joins case detection/foundation records with the selected review's staff events, decisions, observations, policy verdicts, tool results and handoff record. Each decision shows component-labelled input/output activities and the current saved end state. Earlier reviews are selectable and retain their recorded model mode. The API rechecks staff clinic access; viewing/polling makes no model calls. New detections save the validated synthetic candidate snapshot. Historical missing payloads are labelled; exact prompts and individual HTTP attempts are not reconstructed. No database migration is required. See [CASE_JOURNEY.md](CASE_JOURNEY.md).

`FollowupCase.state` remains `NEW`. Agent runs have their own status. An escalated run is not complete until a named staff member accepts its handoff and the Coordinator verifies that evidence. This completes automation only; the staff task remains open. The separate simulated confirmation outcome needs source and acknowledgement evidence, with no handoff. No appointment is booked or rescheduled, and no actual attendance or clinical resolution is claimed.

Six runtime tables store runs, steps, delegations, staff events, handoffs and the shared budget; migration `0004` adds simulated outgoing messages. Original migration `0001` is unchanged. The mock source has its own database and human-operated editor, plus a narrowly authenticated confirmation endpoint. Other source operations remain reads. Three agents are logical roles, not three independently deployed services. No LangGraph dependency is used.

## Still pending

Real patient identity/consent, staff MFA, a patient-facing app, real text/voice delivery, preference storage, source-owned booking writes, reviewed uploads, WhatsApp/SMS/telephone, push/calendar, Singpass, clinically reviewed content/policies, retention controls, Terraform and cloud hosting are not implemented. The local simulator is a test channel only. Future features in the historical design pack should not be presented as delivered.

The application is local and synthetic, with the web port bound to 127.0.0.1. Existing HTTP session authentication does not make it suitable for public hosting or real patient data. Distributed login limits and reviewed immutable deployment image/action references remain deployment work.
