## Completion and data boundary

**Routine confirmation false-positive correction (15 September):** the complete routine confirmation “yes I attend, What should I bring?” is now recognised before model planning. `REPORT_SYMPTOMS` is excluded for replies fully matching the bounded confirmation/preparation grammar, and the gateway independently rejects administrative confirmation/preparation quotes as symptom evidence. Mixed messages with additional symptom content do not match that complete-message grammar and retain the clinical reporting path. This is an additional guard against a demonstrated false positive, not a clinically validated semantic classifier.

**Clinical symptom callback flow (15 September):** current patient symptom reports can now produce typed `REPORT_SYMPTOMS`, with exact reply-bound symptom quotes and a separate attendance-intention quote. The gateway validates evidence and the worker saves a patient acknowledgement, clinical-review checkpoint and RED `PATIENT_REPORTED_SYMPTOMS` handoff together. RED denotes clinical review, not assessed medical urgency. Routine source writes stop; patient-stated intention is not a source confirmation receipt. The assigned staff owner must record a contact/review outcome to resolve the task; accepting it alone keeps it open. This supersedes the earlier “text symptom reporting not implemented” statements for the local simulator. It does not implement clinically validated triage, real calls, voice detection, or guaranteed callback timing. See [clinical review testing](CLINICAL_REVIEW.md).

**Natural reminder replies and specific clarification (15 September):** the existing-appointment reminder path now supports typed `INTERPRET_ATTENDANCE`, in addition to offered-slot interpretation. Engagement classifies unconditional acceptance versus a request for clarification, plus unsupported side-question categories including parking. The gateway binds the saved reply, current source step and active delegation; the source API still validates and records the confirmation. A tentative acceptance produces a persisted clarification naming the source appointment date/time, waits without writing or escalating, and can resume on a later “yes”. The model classifies parking; fixed text acknowledges that parking availability cannot be checked. General unsupported non-clinical questions retain the generic limitation sentence. The old exact-phrase fast path is retained for supported explicit confirmations; natural reminder replies now have an agent interpretation path instead of relying on that grammar alone. No new migration or real patient channel is introduced.

**Unsupported questions alongside slot selections (15 September):** Engagement's typed selection now includes `unsupported_question` (`NONE`, `WEATHER`, `OTHER_NON_CLINICAL`). The saved, gateway-validated interpretation supplies a fixed limitation sentence in the acknowledgement, or in the clarification when no unconditional choice exists. Weather uses “Sorry, I can’t check the weather forecast here.” Other non-clinical questions use “Sorry, I can’t check that information here.” No weather lookup or staff handoff is added for these topics. Clinical/preparation questions are excluded from the generic category; existing blood-test callback behavior remains. This applies to the offered-slot interpretation path, not a general-purpose question-answering service or all initial-message paths.

**Preparation-note timing (15 September):** new slot offers show dates/times and the selection question without general doctor notes. Exact approved instructions appear in the acknowledgement after source-confirmed booking, rescheduling or attendance confirmation. Preparation evidence and prerequisite checks still gate eligibility; this change does not classify free-text notes as scheduling prerequisites. Earlier saved messages retain their original text.

**Agent-interpreted option selection (15 September):** this supersedes the phrase grammar described below. Live booking no longer uses `selected_option` phrase matching. Engagement receives the saved patient reply and offered options, then emits typed `INTERPRET_SELECTION` with `offer_id`, `reply_event_id` and nullable `option_number`. The policy gateway requires current clinic authority, active Engagement delegation, source evidence and the matching saved offer/reply; it rejects invalid option numbers and foreign/stale references. A permitted selection is persisted with its decision-step provenance. The worker then invokes the existing guarded source action. A null selection displays a short clarification and waits without repeating the slots or changing the appointment. Interpretation is model evidence, not proof of real patient identity/consent; the feature remains a staff-operated synthetic channel. Deterministic phrase matching remains only in the offline MockModel fixture. Patient prompts no longer prescribe a response template. The complete JSON schema was regenerated.

**Natural option selection and patient wording (15 September):** supported whole-message selections now include “option 1 ok for me”, “Option 1 works for me”, “I'll take option 1” and the original “Book option 1”. Each resolves only against the same run's latest saved offer; questions, negations, conditions and conflicting choices do not authorize a write. The generic test-information disclaimer and instruction to call the clinic were removed from slot offers. The prompt asks which option works for the patient. This is a bounded explicit-selection grammar, not unrestricted natural-language consent; source and gateway checks remain unchanged. Earlier messages are retained as historical evidence.

**Available slots and rescheduling (15 September):** slot queries now work for existing scheduled appointments as well as recalls. The Coordinator can display source options even when new-recall booking is unavailable. Listing does not modify the source appointment. An exact `Book option N` selection is bound to the latest persisted offer; the worker calls the source-owned synthetic rescheduling endpoint, which rechecks episode/slot versions and availability atomically. The acknowledgement states the old and new times. A stale selection produces current alternatives and an AMBER `SLOT_SELECTION_CHANGED` staff task, preserving the existing appointment. No available slots produces an explicit message and `NO_AVAILABLE_SLOTS` handoff. No temporary holds, automatic alternative selection, waitlists or repeated booking retries are implemented. A last-instant source conflict also rejects the write and uses the existing bounded staff fallback. Historical runs remain unchanged. This supersedes the earlier rescheduling limitation below.

**Clinic callback after confirmation (15 September):** supported confirmation plus blood-test questions retain the successful attendance receipt and create an AMBER `PATIENT_QUESTION_CALLBACK` task atomically with the acknowledgement. Patient wording says a callback was requested, not promised. The UI separates confirmed attendance from the open question. Named staff acceptance keeps the case escalated/open; the owner must record a contact outcome through authenticated `resolve_callback` before completion. Neither staff action requires another model call. Question/evidence/status live in the existing persisted run checkpoint, ownership in `staff_handoff`, and acceptance/resolution in `agent_event`; no schema migration is needed. This supersedes the earlier completion behavior for mixed blood-test questions. Free-text notes are not treated as proof that the specific question was answered, so these supported questions conservatively go to staff. No actual callback is placed.

**Confirmation with blood-test question (15 September):** the explicit-confirmation grammar now accepts supported independent blood-test record questions after a clear positive confirmation, including “I confirm my attendance, do i have any blood test on the day?”.
