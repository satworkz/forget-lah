# Implementation status

## M2a: local agent runtime — v0.2.0

Implemented on top of M1: three logical agents in a persistent Python worker; Coordinator-only delegation; six strict decision types; role-specific source read tools; saved observations, decisions, gateway verdicts and tool results; specialist intent/evidence reports; durable waiting/resumption; staff pause/retry controls; escalation and named staff acceptance; a staff timeline; forward database migration `0002`; an organiser JSON HTTP adapter; an explicitly labelled deterministic simulation; bounded retries, steps, request sizes and a shared live-call budget.

**Direct Claude addition (11 September):** `anthropic` mode uses the Messages API through the same typed decision/policy boundary. Migration `0003` preserves runs and allows the new provider. Both live providers and the one-call `model-check` share the persisted call limit and pacing. Provider credentials are backend-only. Follow [CLAUDE_SETUP.md](CLAUDE_SETUP.md). Direct Claude is now connected and tested with paid synthetic dental reviews. The direct adapter uses native JSON schema constraints, followed by the same strict parser and policy gateway. See [live validation](LIVE_CLAUDE_VALIDATION.md) for the outcomes, including earlier rejected attempts.

The organiser adapter follows the public starter-kit protocol and is tested using simulated HTTP responses. **The organiser endpoint has not been live-verified: its private team API URL/key have not been supplied.** Default mode is `mock`; model, mock and rule origins are distinct. No failed organiser call falls back to simulation.

Dental, myopia and antenatal cases use the shared runtime. A mixed date/preparation request exercises both specialists. Reply intent is unverified staff-entered demo data. A staff clinical flag creates a rule-origin RED handoff without requiring a model. Automatic clinical text/voice detection is pending.

**Unsupported RED correction (14 September):** model escalation choices now exclude `CLINICAL_REVIEW_REQUIRED`; the gateway independently denies it and preserves the rejected proposal. RED requires the existing explicit staff clinical flag. Routine confirmations with unavailable patient messaging/attendance updates use an AMBER administrative handoff. Handoff risk comes from the gateway, not the model's reason code. A scoped maintenance correction can appear as a separate journey event, preserving the original decision, verdict and original handoff classification.

M1 authentication, current clinic membership checks, Origin/CSRF protection, synthetic detection and leased foundation jobs remain. The old two-action draft validator is replaced by the current runtime contract; see [agent-decision-v1.json](contracts/agent-decision-v1.json).

## Completion and data boundary

**Routine confirmation false-positive correction (15 September):** the complete routine confirmation “yes I attend, What should I bring?” is now recognised before model planning. `REPORT_SYMPTOMS` is excluded for replies fully matching the bounded confirmation/preparation grammar, and the gateway independently rejects administrative confirmation/preparation quotes as symptom evidence. Mixed messages with additional symptom content do not match that complete-message grammar and retain the clinical reporting path. This is an additional guard against a demonstrated false positive, not a clinically validated semantic classifier.

**Clinical symptom callback flow (15 September):** current patient symptom reports can now produce typed `REPORT_SYMPTOMS`, with exact reply-bound symptom quotes and a separate attendance-intention quote. The gateway validates evidence and the worker saves a patient acknowledgement, clinical-review checkpoint and RED `PATIENT_REPORTED_SYMPTOMS` handoff together. RED denotes clinical review, not assessed medical urgency. Routine source writes stop; patient-stated intention is not a source confirmation receipt. The assigned staff owner must record a contact/review outcome to resolve the task; accepting it alone keeps it open. This supersedes the earlier “text symptom reporting not implemented” statements for the local simulator. It does not implement clinically validated triage, real calls, voice detection, or guaranteed callback timing. See [clinical review testing](CLINICAL_REVIEW.md).

**Natural reminder replies and specific clarification (15 September):** the existing-appointment reminder path now supports typed `INTERPRET_ATTENDANCE`, in addition to offered-slot interpretation. Engagement classifies unconditional acceptance versus a request for clarification, plus unsupported side-question categories including parking. The gateway binds the saved reply, current source step and active delegation; the source API still validates and records the confirmation. A tentative acceptance produces a persisted clarification naming the source appointment date/time, waits without writing or escalating, and can resume on a later “yes”. The model classifies parking; fixed text acknowledges that parking availability cannot be checked. General unsupported non-clinical questions retain the generic limitation sentence. The old exact-phrase fast path is retained for supported explicit confirmations; natural reminder replies now have an agent interpretation path instead of relying on that grammar alone. No new migration or real patient channel is introduced.

**Unsupported questions alongside slot selections (15 September):** Engagement's typed selection now includes `unsupported_question` (`NONE`, `WEATHER`, `OTHER_NON_CLINICAL`). The saved, gateway-validated interpretation supplies a fixed limitation sentence in the acknowledgement, or in the clarification when no unconditional choice exists. Weather uses “Sorry, I can’t check the weather forecast here.” Other non-clinical questions use “Sorry, I can’t check that information here.” No weather lookup or staff handoff is added for these topics. Clinical/preparation questions are excluded from the generic category; existing blood-test callback behavior remains. This applies to the offered-slot interpretation path, not a general-purpose question-answering service or all initial-message paths.

**Preparation-note timing (15 September):** new slot offers show dates/times and the selection question without general doctor notes. Exact approved instructions appear in the acknowledgement after source-confirmed booking, rescheduling or attendance confirmation. Preparation evidence and prerequisite checks still gate eligibility; this change does not classify free-text notes as scheduling prerequisites. Earlier saved messages retain their original text.

**Agent-interpreted option selection (15 September):** this supersedes the phrase grammar described below. Live booking no longer uses `selected_option` phrase matching. Engagement receives the saved patient reply and offered options, then emits typed `INTERPRET_SELECTION` with `offer_id`, `reply_event_id` and nullable `option_number`. The policy gateway requires current clinic authority, active Engagement delegation, source evidence and the matching saved offer/reply; it rejects invalid option numbers and foreign/stale references. A permitted selection is persisted with its decision-step provenance. The worker then invokes the existing guarded source action. A null selection displays a short clarification and waits without repeating the slots or changing the appointment. Interpretation is model evidence, not proof of real patient identity/consent; the feature remains a staff-operated synthetic channel. Deterministic phrase matching remains only in the offline MockModel fixture. Patient prompts no longer prescribe a response template. The complete JSON schema was regenerated.

**Natural option selection and patient wording (15 September):** supported whole-message selections now include “option 1 ok for me”, “Option 1 works for me”, “I'll take option 1” and the original “Book option 1”. Each resolves only against the same run's latest saved offer; questions, negations, conditions and conflicting choices do not authorize a write. The generic test-information disclaimer and instruction to call the clinic were removed from slot offers. The prompt asks which option works for the patient. This is a bounded explicit-selection grammar, not unrestricted natural-language consent; source and gateway checks remain unchanged. Earlier messages are retained as historical evidence.

**Available slots and rescheduling (15 September):** slot queries now work for existing scheduled appointments as well as recalls. The Coordinator can display source options even when new-recall booking is unavailable. Listing does not modify the source appointment. An exact `Book option N` selection is bound to the latest persisted offer; the worker calls the source-owned synthetic rescheduling endpoint, which rechecks episode/slot versions and availability atomically. The acknowledgement states the old and new times. A stale selection produces current alternatives and an AMBER `SLOT_SELECTION_CHANGED` staff task, preserving the existing appointment. No available slots produces an explicit message and `NO_AVAILABLE_SLOTS` handoff. No temporary holds, automatic alternative selection, waitlists or repeated booking retries are implemented. A last-instant source conflict also rejects the write and uses the existing bounded staff fallback. Historical runs remain unchanged. This supersedes the earlier rescheduling limitation below.

**Clinic callback after confirmation (15 September):** supported confirmation plus blood-test questions retain the successful attendance receipt and create an AMBER `PATIENT_QUESTION_CALLBACK` task atomically with the acknowledgement. Patient wording says a callback was requested, not promised. The UI separates confirmed attendance from the open question. Named staff acceptance keeps the case escalated/open; the owner must record a contact outcome through authenticated `resolve_callback` before completion. Neither staff action requires another model call. Question/evidence/status live in the existing persisted run checkpoint, ownership in `staff_handoff`, and acceptance/resolution in `agent_event`; no schema migration is needed. This supersedes the earlier completion behavior for mixed blood-test questions. Free-text notes are not treated as proof that the specific question was answered, so these supported questions conservatively go to staff. No actual callback is placed.

**Confirmation with blood-test question (15 September):** the explicit-confirmation grammar now accepts supported independent blood-test record questions after a clear positive confirmation, including “I confirm my attendance, do i have any blood test on the day?”. Conditional or contradictory suffixes remain blocked. The acknowledgement preserves approved notes and explicitly distinguishes the confirmed attendance from any test information still requiring clinic clarification. This remains a bounded English simulator grammar, not general natural-language consent or clinical triage.

After Engagement obtains current source evidence, an already-authorized simulated confirmation/slot selection is executed as the rule `EXPLICIT_SIMULATED_CONFIRMATION` through the normal policy gateway and source adapter, with zero model attempts. The source still checks status, time, revision, prerequisite and any selected slot. This avoids asking Claude to reconsider established simulator permission based on disabled real-world contact flags. The agents still delegate, gather evidence and review/report preparation; failed source writes follow the existing bounded recovery path.

**Recall slot simulator (14 September):** clear date requests for due recalls now gather Engagement source evidence and Preparation notes/prerequisites. Coordinator displays dated source slots and exact approved notes, then waits for an explicit `Book option N` reply. The mock clinic API atomically claims the source slot and records a scheduled appointment/confirmation receipt; updated preparation evidence precedes acknowledgement and completion. Source migration `sim0003` preserves booking provenance. No real messages or bookings occur. Missing test information is left for clinic clarification, never interpreted as no test required. Existing appointment rescheduling and automatic slot-conflict recovery remain pending. This supersedes the earlier no-simulated-booking boundary below. See [Patient simulator](PATIENT_SIMULATOR.md).

**Live-test refinements (15 September):** after a demo reply arrives, the model cannot choose another patient-reply wait; the gateway checks this independently. Displaying options saves the wait as part of the permitted tool action. Preparation and final Coordinator phases receive shorter, role-specific instructions. Model context previews at most three slots and reports the saved count; full source results remain in step history and all returned slots are displayed to the patient. Explicit retries can preserve ready completion evidence after a request-size pause, without another booking or relaxed limits.

**Repeated-read recovery (14 September):** per-event successful reads are removed from the model's offered tools and rejected independently by the gateway. The Coordinator reuses context returned by either role; specialists still require their own evidence. When acknowledgement evidence is ready, the model can acknowledge or escalate, then complete or escalate. An explicit retry of an older Coordinator role-budget pause can preserve ready completion evidence without replaying specialist work; overall step and daily-call limits remain unchanged.

**Patient conversation simulator (14 September):** new reviews display a persisted reminder, record an explicit synthetic attendance confirmation through a narrow mock clinic API, display an acknowledgement with exact approved notes, and complete without handoff after verifying receipt/message evidence. Coordinator delegates to Engagement and Preparation; the gateway owns authorization and completion checks. The source verifies appointment status/date/revision and prerequisite. No scheduling or booking change is made. Outgoing messages are local-only. Application migration `0004` adds `simulated_message`; source migration `sim0002` adds `sim_confirmation`. Idempotency, bounded source retries and late receipt recording cover interrupted writes. Fresh simulator tests preserve prior reviews. See [Patient simulator](PATIENT_SIMULATOR.md).

**Dynamic clinic simulator (13 September):** a separate local page combines schedule/status editing, synthetic notes and specialty-level available slots. The mock service persists three tables in its own `forget_lah_mock` database/user on the existing PostgreSQL server. Bootstrap provisions/migrates/seeds automatically; source migration `sim0001` is separate from application migration `0003`. The authenticated editor proxy uses clinic/Origin/CSRF checks and an internal key unavailable to the worker. Revision checks reject stale edits. Source URLs remain unchanged, with optional slot evidence added to context. Fresh `SIM-...` episodes are detected automatically; source edits do not restart existing cases or rewrite history. Reset supports the complete validated snapshot and recreates only eligible cases. See [Clinic simulator](CLINIC_SIMULATOR.md).

**Automatic startup and source loading (13 September):** new cases queue a review in the same transaction that completes the foundation job. A bounded recovery scan picks up older ready cases with no review. Existing reviews of any status are never restarted by this scan. The worker uses a reserved non-login principal with demo-clinic membership; bootstrap provisions it once without re-enabling revoked access. Gateway checks distinguish service authority from staff authority. Staff replies and handoff acceptance still require authenticated clinic access. `AGENT_AUTO_START_ENABLED` defaults to true; false stops new automatic registrations, not existing runs. Missing model configuration is shown as a paused review. No schema migration was required.

The first normal source read is a typed, persisted `origin=rule` tool action with zero model attempts, executed through the usual gateway/adapter and lease/version checks before model planning. Failed reads remain explicit results for recovery. Staff-flagged clinical escalation bypasses routine loading. Pending historical model steps retain their provenance. The initial-read optimisation applies to the first step of a new review; later context-dependent tool choices remain agent decisions. Both dashboard start buttons are removed; pause, retry, demo reply, handoff and optional reset controls remain. The authenticated manual-start API is retained for compatibility and engineering tests; the dashboard no longer calls it.

**Initial wait optimisation (12 September):** after Coordinator delegation to Engagement, the worker uses the current event's successful source context to save the fixed initial demo wait without a model call. This requires an active delegation and explicit disabled contact/write capabilities. The typed WAIT still passes the gateway and is persisted as `origin=rule`, with zero attempts and no live-call reservation. Missing/failed evidence retains the normal agent/recovery path; resumed replies still use model decisions. Existing historical decisions are preserved. The rule is one recorded step within the existing 24-step guardrail; that count is not a count of Claude calls.

**Demo reset addition (12 September):** `DEMO_RESET_ENABLED` defaults to false. When enabled, authorised demo-clinic staff can type `RESET` in the dashboard confirmation to atomically clear demo case/history records and recreate the three validated source candidates. Accounts, sessions, other clinics and usage accounting are preserved. Queued/running reviews must be paused first. The API checks Origin/CSRF, current membership, expected case IDs and fixture identity, and refuses reset if the source is unavailable. PostgreSQL table locks prevent overlapping resets/mutations; stale requests cannot reset a new generation. No migration is needed. See [DEMO_RESET.md](DEMO_RESET.md).

**Case Journey addition (12 September):** a separate read-only page joins case detection/foundation records with the selected review's staff events, decisions, observations, policy verdicts, tool results and handoff record. Each decision shows component-labelled input/output activities and the current saved end state. Earlier reviews are selectable and retain their recorded model mode. The API rechecks staff clinic access; viewing/polling makes no model calls. New detections save the validated synthetic candidate snapshot. Historical missing payloads are labelled; exact prompts and individual HTTP attempts are not reconstructed. No database migration is required. See [CASE_JOURNEY.md](CASE_JOURNEY.md).

`FollowupCase.state` remains `NEW`. Agent runs have their own status. An escalated run is not complete until a named staff member accepts its handoff and the Coordinator verifies that evidence. This completes automation only; the staff task remains open. The separate simulated confirmation outcome needs source and acknowledgement evidence, with no handoff. No appointment is booked or rescheduled, and no actual attendance or clinical resolution is claimed.

Six runtime tables store runs, steps, delegations, staff events, handoffs and the shared budget; migration `0004` adds simulated outgoing messages. Original migration `0001` is unchanged. The mock source has its own database and human-operated editor, plus a narrowly authenticated confirmation endpoint. Other source operations remain reads. Three agents are logical roles, not three independently deployed services. No LangGraph dependency is used.

## Still pending

Real patient identity/consent, staff MFA, a patient-facing app, real text/voice delivery, preference storage, source-owned booking writes, reviewed uploads, WhatsApp/SMS/telephone, push/calendar, Singpass, clinically reviewed content/policies, retention controls, Terraform and cloud hosting are not implemented. The local simulator is a test channel only. Future features in the historical design pack should not be presented as delivered.

The application is local and synthetic, with the web port bound to 127.0.0.1. Existing HTTP session authentication does not make it suitable for public hosting or real patient data. Distributed login limits and reviewed immutable deployment image/action references remain deployment work.
